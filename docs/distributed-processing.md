# Распределённая обработка Pixora

## Что запущено

Локальный стенд состоит из пяти постоянно работающих контейнеров:

- `api` — принимает пакет изображений, создаёт задания и отдаёт статусы;
- `redis` — передаёт задания Celery и хранит их состояния;
- `minio` — хранит исходные изображения и готовые результаты;
- два экземпляра `worker` — независимо забирают задания из очереди и вызывают
  обычный `ImageService` Pixora.

Каждое изображение является отдельной вычислительной задачей. Поэтому разные
изображения одного пакета могут одновременно обрабатываться разными workers.

## Что видно в приложении

Экран пакетной обработки содержит живую схему
`FastAPI → Redis → Workers → MinIO`. Данные берутся из работающего кластера:

- зелёные карточки показывают доступные сервисы и свободные workers;
- фиолетовая карточка означает, что worker выполняет задачу;
- красная карточка означает потерю связи с сервисом или worker;
- Redis показывает количество задач, ожидающих в очереди;
- рядом с каждым файлом отображается назначенный `Worker 1`, `Worker 2` и так
  далее;
- после завершения показываются количество файлов на каждом worker и общее
  время пакета.

В подсказке карточки worker сохраняется его настоящий Celery-идентификатор.
Поэтому понятное визуальное имя не скрывает техническое доказательство того,
что задачи выполнялись разными контейнерами.

## Запуск локального кластера

Из корня проекта:

```powershell
docker compose up --build --detach
docker compose ps
```

После запуска доступны:

- API: <http://127.0.0.1:8000>;
- Swagger: <http://127.0.0.1:8000/docs>;
- MinIO Console: <http://127.0.0.1:9001>.

Данные Redis и MinIO находятся в именованных Docker volumes. Метаданные задач и
файлы автоматически удаляются через 24 часа. Исходник также удаляется сразу
после успешной обработки или подтверждённой отмены.

## Быстрая проверка

```powershell
python scripts/distributed_smoke_test.py
```

Скрипт выполняет полный путь:

1. создаёт восемь временных PNG с разными соотношениями сторон;
2. отправляет их одним пакетом в FastAPI;
3. ждёт завершения Celery-задач;
4. проверяет участие минимум двух workers;
5. скачивает результаты из MinIO через API;
6. проверяет формат, размеры и отсутствие искажений пропорций.

Если включено «Сохранять пропорции», каждое изображение независимо вписывается
в выбранные границы ширины и высоты. Если флажок отключён, все результаты имеют
точно указанный размер.

## Масштабирование

Число worker-контейнеров можно изменить без правок Python-кода:

```powershell
docker compose up --detach --scale worker=4
```

Redis отдаёт свободное задание следующему доступному worker. Параметр
`worker_prefetch_multiplier=1` не позволяет одному узлу заранее забрать большую
часть коротких заданий.

## Остановка

```powershell
docker compose down
```

Команда останавливает контейнеры, но сохраняет результаты и данные очереди.
Удалять volumes следует только тогда, когда тестовые данные больше не нужны.

## Переменные окружения

Пример локальных реквизитов находится в `.env.example`. Для тестового стенда
Compose подставляет локальные демонстрационные значения. Перед запуском в общей
сети нужно задать собственный длинный пароль MinIO и не публиковать Redis без
аутентификации и сетевого ограничения.

Desktop-приложение по умолчанию обращается к
`http://127.0.0.1:8000`. Другой адрес можно передать через переменную
`PIXORA_API_URL` до запуска Pixora.

## HTTP API

- `GET /health` — готовность Redis и MinIO;
- `GET /api/v1/cluster` — состояние сервисов, очередь и активные workers;
- `POST /api/v1/batches` — загрузка пакета и постановка задач в очередь;
- `GET /api/v1/batches/{batch_id}` — общий прогресс и состояния файлов;
- `POST /api/v1/batches/{batch_id}/cancel` — отмена незавершённых задач;
- `GET /api/v1/jobs/{job_id}` — состояние одной задачи;
- `GET /api/v1/jobs/{job_id}/download` — скачивание готового результата.

В ответе успешной задачи есть поле `worker`. Разные значения этого поля для
одного пакета являются наглядным подтверждением распределения вычислений.

## Демонстрация на защите

1. Запустить кластер и убедиться, что в «Живом кластере» доступны два workers.
2. Выбрать не менее восьми изображений и запустить пакетную обработку.
3. Показать, как карточки workers переходят в состояние «занят», а строки
   файлов получают разные назначения и цвета.
4. После завершения показать итоговое распределение файлов между узлами.
5. Для демонстрации отказоустойчивости остановить один worker и обновить
   монитор: его карточка станет красной, а доступный узел продолжит забирать
   задания из Redis.

Отмена хранится в Redis, поэтому ожидающая задача останется отменённой даже в
том случае, если worker был выключен во время запроса и подключился позднее.
